# WHYLOG 产品说明

## 要解决的问题

AI 把代码与内容的生成速度推高后，用户的工作重心从执行转向高密度抉择。代码保存了 What，AI 处理了 How，但项目最容易丢失的是 Why：当时的问题、已知约束、排除 A 的原因、选择 B 接受的代价，以及什么变化会使选择失效。

## 核心用户

同时推进多个软件、内容与创业项目的独立创造者。当前以单人使用为主，会让多个 AI 执行，但需要自己保留最终判断权与纵向决策数据。

## MVP 工作流

1. 用 Job to Be Done 判断这个决定是否值得进入工程。
2. 把已知事实与待验证假设物理分层，并标注来源与置信度。
3. 写出决策驱动、硬约束以及至少两个候选方案。
4. 明确选择理由，同时记录收益、代价和风险。
5. 定义执行确认方法与条件变化后的重审触发器。
6. 在固定日期或触发条件出现后，记录现实结果、证据、核心教训和未来规则。
7. 将完成复盘的「未来规则」自动回流到规则库，并在下一条相关决策中显示来源；可按上下文、选择理由、教训与规则搜索旧决策。
8. 将完整记录导出为 MADR 4.0 兼容 Markdown，放入项目 `docs/decisions/` 并随 Git 管理。
9. 将全部浏览器数据备份为 JSON，必要时在另一环境恢复。

## 明确不做

- 不让 AI 自动替用户做最终选择。
- 不在 MVP 中加入云账号、在线数据库、实时协作或审批流。
- 不改写仓库原有 `decisions/`、`index.json` 与 `patterns.md` 历史数据。
- 不假装完整度分数等于决策正确；分数只检查记录是否可评审。

## 成功标准

- 空白 ADR 的缺失项可解释；完整示例得分 100。
- 页面刷新后数据仍在，错误数据不会静默覆盖。
- 导出的 Markdown 包含 MADR 核心段落、WHYLOG 扩展段落和可排序文件名。
- 已采纳且到期的记录进入「待复盘」筛选；完成复盘后从该筛选消失，并在 Markdown 中留下 Outcome Review。
- 完整复盘生成只读规则；新决策能看到相关过往规则及其 ADR 来源，深层搜索能命中上下文、选择理由、结果、教训与未来规则。
- 旧版 v1 工作区缺少结果字段时可读取并补齐默认值；删除或导入替换后在下一次编辑前保留可见撤销入口。
- 桌面和移动布局均能创建、编辑、筛选、备份和导出，不发生横向溢出。
- Playwright 与 axe 检查不报告 WCAG A/AA 自动化违规。
